# 标准工作流

本文定义所有参与者都应遵循的同一条生产流程。个人偏好可以改变译名与文风，但不能绕过证据、冻结身份、验收和发布门禁。

## 角色

| 角色 | 责任 | 不得做的事 |
|---|---|---|
| 项目负责人 | 确认版权、范围、目标读者与最终验收 | 把密钥或受限原文提交到 Git |
| 术语审校者 | 用原书证据建立义项、批准冻结快照 | 边翻边改当前快照 |
| 构建执行者 | 预扫描、验收、全量构建、恢复失败 chunk | 绕过构建身份检查复用旧缓存 |
| 内容审校者 | 对照原文检查事实、逻辑、术语和格式 | 直接改生成的章节文件而不留 review 记录 |
| 发布者 | 只发布通过门禁的候选，核对目标目录 | 覆盖已有笔记或把构建缓存放入 Vault |

一个人可以兼任多个角色，但每项责任都必须完成。

## 阶段 0：立项与边界

1. 确认对源材料具有合法使用权。
2. 明确范围：全书、正文或指定章节；明确是否包含图片视觉转写。
3. 明确质量目标：个人精读、团队内部参考或出版级编辑。Bilingua 默认只承诺前两者。
4. 为项目建立独立工作目录；代码仓库、原书与 Obsidian Vault 分离。

产出：范围说明、书籍 slug、目标语言、发布位置。

## 阶段 1：初始化与诊断

```bash
bilingua init /path/to/project
cd /path/to/project
cp .env.example .env
bilingua doctor --project-root .
```

通过条件：`doctor` 全部为 `OK`。它不联网，不验证远端模型质量；API 能力需用单独的小样本确认。

## 阶段 2：预扫描

把合法取得并转换好的 Markdown 放入 `source/`，执行：

```bash
bilingua inspect source/book.md --book-slug book
```

检查：

- 章节边界是否正确；
- 最大 chunk 是否低于提供商输出上限；
- 表格、图片、代码和原始 HTML 是否被正确识别；
- 是否存在标题层级塌陷，需要增加 `--chapter-level 2`；
- 图片是否含有必须转写的关键信息。

产出：预扫描报告、验收章节选择、图片处理决定。

## 阶段 3：术语证据与冻结

术语采用 global / domain / book 三层义项模型。每条批准义项至少应有：

- 稳定 ID、英文 surface、中文首选译名；
- 作者或适用范围；
- 中文定义；
- 至少一个原书段落 ID 作为 evidence；
- 选择该译名的 decision；
- `status: approved`。

候选词先进入 `glossary/candidates.yaml`，不会参与当前构建。冻结后生成新文件，不覆盖旧快照：

```bash
bilingua freeze-glossary \
  --root glossary --domain general --book book \
  --output glossary/snapshots/book-v1.lock
```

通过条件：人工审校者确认快照范围与作者立场；构建期间不再修改 v1。

## 阶段 4：代表章节验收

选择概念密度高、结构复杂或图片较多的章节，以 `concurrency=1` 构建。验收至少检查：

- 英中逐段对应，无漏译、错行、逻辑反转与无依据增译；
- 核心术语、数字、年代、链接、脚注和列表保持；
- 作者观点没有被其他作者的定义替代；
- 图片原样保留，视觉旁注明确标注来源与置信度；
- API 延迟、重试率、输出完整率与实际费用可接受。

不通过时回到预扫描、规则或术语阶段。通过后才允许全量构建。

## 阶段 5：全量构建与恢复

完整命令必须固定：源文件、slug、快照、文风卡、章节层级、分块参数、模型与 build root。保存命令供恢复使用。

每个 chunk 成功后会追加写入 `translations.jsonl` 并更新原子状态。中断后重跑相同命令；不要手改 `state.json` 或删除部分日志。

通过条件：全部目标 chunk 为 done，装配前内容校验为 0 错误。

## 阶段 6：独立审校与 review 补丁

审校报告应把确定错误、可讨论文风、原文瑕疵分开。只把有证据的修改写入 review JSON：

```bash
bilingua apply-review --build-dir build-main/book --input reviews/round-1.json
```

补丁必须带 reviewer，按 chunk 和段落 ID 定位。导入后重跑同一构建命令，完成零 API 重校验与重装配。

通过条件：装配前错误、装配缺漏、成品复检错误均为 0；高风险项目由第二人抽查。

## 阶段 7：候选发布与核对

1. 先写临时候选目录；目标正式目录存在时拒绝覆盖。
2. 核对阅读文件、图片、索引、自动报告与构建摘要。
3. 桌面与 Obsidian 双发布时，按相对路径和文件内容计算整树哈希。
4. 一致后才换名为正式目录；旧版移入可恢复备份，不立即删除。

通过条件：两处内容一致，候选目录清零，备份路径记入工作报告。

## Definition of Done

- [ ] 范围、版权与目标质量已记录。
- [ ] 预扫描与代表章节验收已通过。
- [ ] 构建绑定冻结术语快照。
- [ ] 所有目标 chunk 完成且无构建身份混用。
- [ ] 审校修改通过 review 日志导入。
- [ ] 装配前、装配完整性、成品复检均为 0 错误。
- [ ] 图片与视觉旁注按既定范围核验。
- [ ] 正式发布目录和备份均可定位。
- [ ] 工作报告记录模型声明、真实性边界、性能、费用和剩余风险。
